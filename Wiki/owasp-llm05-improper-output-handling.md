# LLM05: Improper Output Handling

> [!abstract] Summary
> Improper Output Handling occurs when downstream systems blindly trust and act on LLM-generated content without validation or sanitization. Because LLM output is user-influenced, it functions as an untrusted input — passing it unsanitized into browsers, shells, databases, or file systems can result in XSS, CSRF, SSRF, SQL injection, path traversal, or remote code execution.

## Definition

> [!quote] OWASP LLM05:2025 — Description
> "Improper Output Handling refers specifically to insufficient validation, sanitization, and handling of the outputs generated by large language models before they are passed downstream to other components and systems. Since LLM-generated content can be controlled by prompt input, this behavior is similar to providing users indirect access to additional functionality."
> — [[Sources/OWASP-LLM/LLM05-improper-output-handling]]

> [!quote] OWASP LLM05:2025 — Impact
> "Successful exploitation of an Improper Output Handling vulnerability can result in XSS and CSRF in web browsers as well as SSRF, privilege escalation, or remote code execution on backend systems."
> — [[Sources/OWASP-LLM/LLM05-improper-output-handling]]

## Attack Examples

> [!quote] OWASP LLM05:2025 — Common Vulnerabilities
> "1. LLM output is entered directly into a system shell or similar function such as exec or eval, resulting in remote code execution.
> 2. JavaScript or Markdown is generated by the LLM and returned to a user. The code is then interpreted by the browser, resulting in XSS.
> 3. LLM-generated SQL queries are executed without proper parameterization, leading to SQL injection.
> 4. LLM output is used to construct file paths without proper sanitization, potentially resulting in path traversal vulnerabilities.
> 5. LLM-generated content is used in email templates without proper escaping, potentially leading to phishing attacks."
> — [[Sources/OWASP-LLM/LLM05-improper-output-handling]]

## Prevention Strategies

> [!quote] OWASP LLM05:2025 — Mitigations
> "1. Treat the model as any other user, adopting a zero-trust approach, and apply proper input validation on responses coming from the model to backend functions.
> 2. Follow the OWASP ASVS (Application Security Verification Standard) guidelines.
> 3. Encode model output back to users to mitigate undesired code execution by JavaScript or Markdown.
> 4. Implement context-aware output encoding based on where the LLM output will be used (e.g., HTML encoding for web content, SQL escaping for database queries).
> 5. Use parameterized queries or prepared statements for all database operations involving LLM output.
> 6. Employ strict Content Security Policies (CSP) to mitigate the risk of XSS attacks.
> 7. Implement robust logging and monitoring systems to detect unusual patterns in LLM outputs."
> — [[Sources/OWASP-LLM/LLM05-improper-output-handling]]

## Key Principle: Treat LLM Output as Untrusted

> [!warning] Zero-Trust Output Rule
> LLM output is never "safe" — it is influenced by user input and external data.
> Always apply the same validation/sanitization you would apply to raw user input before passing to shells, databases, browsers, or APIs.
> Combine with LLM06 (Excessive Agency) controls to limit what downstream systems can actually do with LLM output.

> [!example] Context-Specific Output Handling
> | Downstream Target | Required Handling |
> |---|---|
> | HTML/Browser | HTML-encode; enforce strict CSP |
> | SQL Database | Parameterized queries only — never string concat |
> | File system | Validate path; reject traversal sequences (`../`) |
> | Shell/exec | Never pass LLM output to shell commands |
> | Email templates | Escape all LLM content; validate sender/recipient fields |
> | API calls | Schema-validate LLM output before use as API parameters |
